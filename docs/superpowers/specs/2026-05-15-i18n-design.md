# Frontend i18n (Swedish / English / Finnish) — Design

**Date:** 2026-05-15
**Goal:** Make the frontend UI translatable into English, Swedish, and Finnish. Cover static labels, Zod validation messages, and locale-aware date/number formatting.

---

## Context

The frontend currently ships ~15 hard-coded strings spread across `index.tsx`, `posts.tsx`, `LoginForm.tsx`, `LoginPage.tsx`, `PostsPage.tsx`, `DashboardPage.tsx`, and the `Header` widget. The recent login redesign already mixes Swedish (`E-POST`, `LÖSENORD`, `Logga in`) and English (`Posts`, `New post`, `Loading…`, `Sign in`). Validation messages flow from Zod schemas in `@repo/contracts` and surface untranslated at the form layer.

This design adds a proper i18n layer so language can be selected by the user (defaulting to browser preference, falling back to English) without restructuring routes or splitting bundles.

## Architecture

**Library stack:** `i18next` + `react-i18next` + `i18next-browser-languagedetector`. All three live in `apps/frontend` as production deps.

**Detection chain** (configured in the detector plugin's `order`):
1. `localStorage['i18nextLng']` — set by the switcher
2. `cookie['i18nextLng']` — readable from a future SSR variant
3. `navigator.language` — browser default
4. Static fallback `'en'`

**Persistence:** `i18next-browser-languagedetector` writes both `localStorage['i18nextLng']` and a 1-year `cookie['i18nextLng']` on every `changeLanguage` call.

**Locales:** `en` (source-of-truth), `sv`, `fi`. Three flat JSON files in `apps/frontend/src/i18n/locales/<lang>.json`. Bundled at build time via static `import` — zero runtime fetches.

**No URL prefix.** `/login` is the same URL in all three languages. Routing remains entirely under `app/router/routes/` as-is.

**Initialization:** a single `apps/frontend/src/i18n/index.ts` configures and exports the `i18next` instance. Imported once from `app/main.tsx` *before* the React tree renders, so the first paint already has the resolved language.

```jsonc
{

      "emailLabel": "Email",
      "passwordLabel": "Password",
      "submit": "Sign in",
      "submitting": "Signing in…",
      "failed": "Sign in failed."
    }
  },
  "common": {
    "loading": "Loading…",
    "browse": "Browse posts"
  },
  "posts": {
    "title": "Posts",
    "newPost": "New post",
    "loadFailed": "Failed to load posts: {{message}}"
  },
  "header": {
    "signIn": "Sign in",
    "posts": "Posts"
  },
  "zod": {
    "invalidType": "Expected {{expected}}.",
    "tooSmall": "Must be at least {{min}}.",
```

Usage at call sites:
```tsx
const { t } = useTranslation();

```

## Components

### `<LocaleSwitcher variant?>`

A native `<select>` styled with the existing shadcn primitives. Three options, each labelled with the language's native name:

| Code | Label |
|---|---|
| `en` | English |
| `sv` | Svenska |
| `fi` | Suomi |

On change → `i18n.changeLanguage(value)` → detector writes localStorage + cookie → React tree re-renders (every `useTranslation`-using component subscribes to language changes by default).

`variant` controls the colour palette so the switcher reads correctly on both the default white surface and on the navy hero panel of `/login`:
- `default` (cards, white) — `text-on-surface`, `border-outline-variant`
- `onDark` (hero gradient) — `text-secondary`, `border-on-primary/30`

### Placement

- **Header widget:** rendered inline at the right end of the Header. Visible on `/` and `/posts`.
- **LoginPage (auth):** rendered in the bottom-left of the hero panel with `variant="onDark"`. Necessary because `__root.tsx` hides the global Header for `/login` and `/signup`.

## Zod localization

Zod 4 exposes `z.setErrorMap(errorMap)` — a single global hook that replaces issue → message mapping. We define one error map that calls `i18n.t(...)` per issue code:

```ts
// apps/frontend/src/i18n/zod-error-map.ts
import { type ErrorMap } from 'zod';
import i18n from './index.js';

export const i18nZodErrorMap: ErrorMap = (issue) => {
  switch (issue.code) {
    case 'invalid_type':
      return { message: i18n.t('zod.invalidType', { expected: issue.expected }) };
    case 'too_small':
      return { message: i18n.t('zod.tooSmall', { min: issue.minimum }) };
    case 'too_big':
      return { message: i18n.t('zod.tooBig', { max: issue.maximum }) };
    case 'invalid_string':
      if (issue.validation === 'email') {
        return { message: i18n.t('zod.invalidEmail') };
      }
      return { message: i18n.t('zod.invalidString') };
    default:
      return { message: i18n.t('zod.fallback') };
  }
};
```

The map is installed once in `i18n/index.ts` after the i18next init resolves:

```ts
await i18n.use(...).init({...});
z.setErrorMap(i18nZodErrorMap);
```

The map closes over the live `i18n` singleton, so calling `parse(...)` *after* `changeLanguage(...)` returns messages in the new language. No per-schema or per-form changes needed in `@repo/contracts`.

## Date/number formatting

`apps/frontend/src/i18n/formatters.ts` — three thin wrappers around `Intl.*` that derive locale from the singleton:

```ts
import i18n from './index.js';

const localeOf = (): string => i18n.resolvedLanguage ?? i18n.language ?? 'en';

export function formatDate(d: Date | string | number, opts?: Intl.DateTimeFormatOptions): string {
  const date = d instanceof Date ? d : new Date(d);
  return new Intl.DateTimeFormat(localeOf(), opts).format(date);
}

export function formatNumber(n: number, opts?: Intl.NumberFormatOptions): string {
  return new Intl.NumberFormat(localeOf(), opts).format(n);
}

export function formatRelative(d: Date | string | number): string {
  // returns "in 2 days" / "i går" / "5 minuuttia sitten" etc. via Intl.RelativeTimeFormat
}
```

Call sites that render `post.createdAt` directly (e.g. `PostCard`) switch to `formatDate(post.createdAt)`. Components don't need a hook — they already re-render on language change via `useTranslation()`'s subscription higher up the tree.

## Data flow

**Boot:**
1. `main.tsx` imports `./i18n` (top of file). The import runs `i18next.init(...)`.
2. The detector plugin reads localStorage → cookie → navigator → `'en'`.
3. `z.setErrorMap(i18nZodErrorMap)` registers.
4. React tree renders. `useTranslation()` subscribes each consumer to the current language.

**Switch:**
1. User selects `sv` in `<LocaleSwitcher />`.
2. `i18n.changeLanguage('sv')` runs; detector writes localStorage + cookie.
3. Every `useTranslation` subscriber re-renders with the new translations.
4. Any Zod parse from this point uses the Swedish error map.

**First-visit detection:**
1. No `i18nextLng` in localStorage/cookie. Detector reads `navigator.language`. If it starts with `sv` → uses `sv`; with `fi` → `fi`; else → `en`.
2. The first paint reflects the detected language.

## Testing

Three new test files; no existing tests are rewritten. The `LoginForm.test.tsx` Swedish-label regexes stay; we add a `beforeEach` that calls `i18n.changeLanguage('sv')` so the dependency on Swedish copy is explicit.

### `i18n/index.test.ts`

- TC1: `i18n.t('common.loading')` returns `'Loading…'` after init (default `en`).
- TC2: `await i18n.changeLanguage('sv')` then same key returns `'Laddar…'`.
- TC3: Same for `fi` → `'Lataa…'`.

### `i18n/zod-error-map.test.ts`

- TC1: With language `en`, `z.string().min(8).safeParse('abc').error?.issues[0]?.message` matches `i18n.t('zod.tooSmall', { min: 8 })`.
- TC2: After `changeLanguage('fi')`, the same parse yields the Finnish message.

### `widgets/locale-switcher/ui/LocaleSwitcher.test.tsx`

- TC1: Renders three options.
- TC2: Selecting `sv` calls `i18n.changeLanguage('sv')` and writes `'sv'` to `localStorage['i18nextLng']`.
- TC3: Re-mounting reads the persisted value (smoke test that the detector round-trips).

### Updated test setup

`apps/frontend/src/test/setup.ts` imports `@/i18n` once so every test boots with a real i18next instance. `localStorage` is per-test (jsdom resets it), so the detector starts clean unless a test explicitly seeds it.

## Error handling

| Failure | Behavior |
|---|---|
| Missing key | i18next falls back to `en`. In dev, `saveMissing: true` logs `[i18n] missing key <key>` to the console. Off in prod. |
| Invalid locale in localStorage/cookie | Detector skips it, tries the next source. Eventually falls back to `'en'`. |
| Zod issue code with no `zod.*` mapping | `default` branch of the error map returns `zod.fallback` (`"Invalid value."` in en). |
| `Intl.*` constructor throws (unknown locale) | Wrap in try/catch in `formatters.ts`, fall through to `en-US`. Practically impossible with locked locale list. |

## Out of scope

- Backend NestJS i18n. Server-side error responses stay English; the frontend wraps them where needed.
- RTL scripts.
- Translation management UI / TMS workflow. Source-of-truth is the JSON files in git.
- Persisting locale to the user record. The current cookie/localStorage approach survives across sessions on the same browser.
- ICU MessageFormat (pluralization beyond i18next's simple `_other` suffix). All three target languages handle plurals with i18next's default cardinal plural rules — if a future feature needs `{count, plural, one {...} other {...}}` style messages, swap the relevant key for `i18next-icu`.

## What's NOT changing

- Routing (`app/router/routes/*`) — no `$lang` segment, no parent layout shuffle.
- Zod schemas in `@repo/contracts` — they keep their default English `.describe(...)` text; the `setErrorMap` overrides the visible message at runtime.
- The Japanese motto on `/login` (`精神一到何事か成らざらん`) stays as a static design element, not translated.
- Backend code — no NestJS changes in this spec.
