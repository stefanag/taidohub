# Frontend i18n Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add English/Swedish/Finnish i18n to the frontend with `i18next` + `react-i18next`, persist the logged-in user's preference to better-auth's user record, and route Zod validation messages + date/number formatting through the active locale.

**Architecture:** Three layers, built bottom-up. Backend adds a `locale` column to `user` and surfaces it via better-auth `additionalFields` (no new endpoint — better-auth's built-in `updateUser` handles writes). Frontend boots a singleton `i18next` instance pre-React, plugs Zod's `setErrorMap` into it, then layers a `<LocaleSwitcher>` widget and an `AuthProvider` effect that reconciles `session.user.locale` with the live language. UI strings move to `t('key')` call-by-call across Header, LoginPage, LoginForm, PostsPage, PostCard, DashboardPage, home route.

**Tech Stack:** i18next 23.x, react-i18next 15.x, i18next-browser-languagedetector 8.x, Zod 4 (existing), Drizzle ORM (existing), better-auth 1.6 (existing), React 19, TanStack Router.

```ts
import i18n from 'i18next';
import LanguageDetector from 'i18next-browser-languagedetector';
import { initReactI18next } from 'react-i18next';

import en from './locales/en.json' with { type: 'json' };
import fi from './locales/fi.json' with { type: 'json' };
import sv from './locales/sv.json' with { type: 'json' };

export const SUPPORTED_LOCALES = ['en', 'sv', 'fi'] as const;
export type SupportedLocale = (typeof SUPPORTED_LOCALES)[number];

void i18n
  .use(LanguageDetector)
  .use(initReactI18next)
  .init({
    resources: {
      en: { translation: en },
      sv: { translation: sv },
      fi: { translation: fi },
    },
    supportedLngs: [...SUPPORTED_LOCALES],
    fallbackLng: 'en',
    interpolation: { escapeValue: false }, // React already escapes
    detection: {
      order: ['localStorage', 'cookie', 'navigator'],
      caches: ['localStorage', 'cookie'],
      lookupLocalStorage: 'i18nextLng',
      lookupCookie: 'i18nextLng',
      cookieMinutes: 60 * 24 * 365, // 1 year
    },
    returnNull: false,
  });

export default i18n;
```

The `with { type: 'json' }` syntax is the modern ESM JSON-import attribute, supported by Vite 8 and tsx.

Create `apps/frontend/src/i18n/zod-error-map.ts`:

```ts
import { z } from 'zod';

import i18n from './index.js';

/**
 * Routes every Zod issue through the active i18n bundle. Registered once
 * from `i18n/index.ts` via `z.setErrorMap(i18nZodErrorMap)`.
 *
 * The map closes over the live `i18n` singleton, so `safeParse(...)` after
 * `i18n.changeLanguage(...)` yields the new language's messages.
 */
export const i18nZodErrorMap: z.ZodErrorMap = (issue, ctx) => {
  switch (issue.code) {
    case z.ZodIssueCode.invalid_type:
      return { message: i18n.t('zod.invalidType', { expected: issue.expected }) };
    case z.ZodIssueCode.too_small:
      return { message: i18n.t('zod.tooSmall', { min: String(issue.minimum) }) };
    case z.ZodIssueCode.too_big:
      return { message: i18n.t('zod.tooBig', { max: String(issue.maximum) }) };
    case z.ZodIssueCode.invalid_string:
      if (issue.validation === 'email') {
        return { message: i18n.t('zod.invalidEmail') };
      }
      return { message: i18n.t('zod.invalidString') };
    default:
      return { message: ctx.defaultError };
  }
};
```

If your Zod 4 version reports a different `ZodIssueCode` or signature, adapt: the runtime behaviour is "match the issue.code string, call `i18n.t(...)` with the right interpolation values". The default branch falls through to Zod's own message for cases we don't translate.

- [ ] **Step 1: Write the module**

Create `apps/frontend/src/i18n/formatters.ts`:

```ts
import i18n from './index.js';

const localeOf = (): string => i18n.resolvedLanguage ?? i18n.language ?? 'en';

/**
 * Format a date in the currently active locale.
 *
 * `opts` accepts the standard `Intl.DateTimeFormatOptions`. With no `opts`,
 * uses the locale's default short date.
 */
export function formatDate(
  d: Date | string | number,
  opts?: Intl.DateTimeFormatOptions,
): string {
  const date = d instanceof Date ? d : new Date(d);
  try {
    return new Intl.DateTimeFormat(localeOf(), opts).format(date);
  } catch {
    return new Intl.DateTimeFormat('en-US', opts).format(date);
  }
}

/**
 * Format a number in the currently active locale.
 */
export function formatNumber(n: number, opts?: Intl.NumberFormatOptions): string {
  try {
    return new Intl.NumberFormat(localeOf(), opts).format(n);
  } catch {
    return new Intl.NumberFormat('en-US', opts).format(n);
  }
}
```

```tsx
import * as React from 'react';
import { useTranslation } from 'react-i18next';

import { authClient, useSession } from '@/features/auth-by-email';
import { cn } from '@/shared/lib/utils';

const OPTIONS = [
  { code: 'en', label: 'English' },
  { code: 'sv', label: 'Svenska' },
  { code: 'fi', label: 'Suomi' },
] as const;

export interface LocaleSwitcherProps {
  /** `default` reads on white surfaces; `onDark` reads on the navy hero. */
  variant?: 'default' | 'onDark';
  className?: string;
}

/**
 * Drop-down that flips the active i18n language. Optimistic: changes i18n
 * immediately, then (if the viewer is authenticated) writes the choice to
 * the better-auth user record in the background — best-effort, no spinner.
 */
export function LocaleSwitcher({
  variant = 'default',
  className,
}: LocaleSwitcherProps): React.ReactElement {
  const { i18n, t } = useTranslation();
  const session = useSession();
  const isAuthed = Boolean(session.data?.user);

  const handleChange = (event: React.ChangeEvent<HTMLSelectElement>) => {
    const next = event.target.value;
    void i18n.changeLanguage(next);
    if (isAuthed) {
      authClient.updateUser({ locale: next }).catch((err) => {
        // eslint-disable-next-line no-console
        console.warn('[locale] failed to persist locale to user record', err);
      });
    }
  };

  const palette =
    variant === 'onDark'
      ? 'bg-transparent text-secondary border-on-primary/30'
      : 'bg-transparent text-on-surface border-outline-variant';

  return (
    <label className={cn('inline-flex items-center gap-2 text-sm', className)}>
      <span className="sr-only">{t('locale.switch')}</span>
      <select
        aria-label={t('locale.switch')}
        value={i18n.resolvedLanguage ?? i18n.language}
        onChange={handleChange}
        className={cn(
          'rounded-sm border px-2 py-1 outline-hidden focus-visible:ring-2',
          palette,
        )}
      >
        {OPTIONS.map((opt) => (
          <option key={opt.code} value={opt.code}>
            {opt.label}
          </option>
        ))}
      </select>
    </label>
  );
}
```

```tsx
import * as React from 'react';

import { useSession } from '@/features/auth-by-email';
import i18n from '@/i18n';

/**
 * `AuthProvider` keeps the active i18n language in sync with the logged-in
 * user's persisted locale (better-auth `user.locale`). It does not own any
 * state itself; `useSession()` is stateless inside better-auth's React client.
 *
 * Flow:
 *  - Anonymous: `session.data?.user` is undefined → effect no-ops.
 *  - On login or session refresh: reconcile i18n if the DB locale differs.
 *  - On logout: locale stays at the last-used value (we don't reset).
 */
export function AuthProvider({
  children,
}: {
  children: React.ReactNode;
}): React.ReactElement {
  const session = useSession();
  const dbLocale = session.data?.user
    ? (session.data.user as { locale?: string }).locale
    : undefined;

  React.useEffect(() => {
    if (!dbLocale) return;
    if (i18n.resolvedLanguage === dbLocale) return;
    void i18n.changeLanguage(dbLocale);
  }, [dbLocale]);

  return <>{children}</>;
}
```

## Notes & gotchas

- **JSON import attribute (`with { type: 'json' }`)** requires TS 5.3+ and a Vite version that respects it. We're on TS 6 and Vite 8 — both fine. If you see `Module ... does not provide an export named 'default'`, swap to `import en from './locales/en.json';` (plain) and add `"resolveJsonModule": true` to base.json (it's already there).
- **Zod `setErrorMap` signature** can vary slightly between Zod 3 and Zod 4. The implementation in Task 5 uses `z.ZodErrorMap` typed import; if your installed Zod uses a different name (`z.ErrorMapCtx`, etc.), the test still asserts behaviour — adapt the type imports to match the installed declarations.
- **`useSession()` mocking in tests:** `vi.spyOn(authApi, 'useSession').mockReturnValue(...)` is what the test files in this plan use. If your installed `react-i18next` upgrades and exposes a different `data` shape, the cast in `AuthProvider.tsx` (`session.data.user as { locale?: string }`) provides forward-compat.
- **Test setup order:** `apps/frontend/src/test/setup.ts` must import `@/i18n` early so the singleton is initialised before any test file runs. If a test imports `react-i18next` before `@/i18n`, it'll see an uninitialised instance.
- **Storybook:** stories that render `useTranslation()` consumers need i18n initialised in `.storybook/preview.tsx`. Out of scope here — Storybook continues to work because nothing in the plan removes existing setup, but new stories rendering translated text will need a `decorator` that wraps in `Suspense`. Cross that bridge when a story breaks.
