# CLAUDE.md: TaidoHub

A digital training companion for a Japanese martial-art federation: belt ranks, patterns/techniques,
grading requirements, student progression, and organisation hierarchy. pnpm + Turborepo monorepo:
NestJS backend, React (FSD) frontend, a shared Zod `@repo/contracts` package as the HTTP boundary.

**Stack**: NestJS 11 + Drizzle ORM over PostgreSQL (self-hosted on Hetzner in staging and
production; native Postgres locally) + better-auth (sessions) + CASL (authorization). React 19 + Vite +
TanStack Router/Query + Tailwind + shadcn/ui, organised by Feature-Sliced Design v2.1.
`@repo/contracts`: Zod schemas with `.meta()` metadata are the single source of truth for DTOs,
runtime validation, the generated OpenAPI spec, and shared TS types. See [README.md](README.md) for
full setup and [DESIGN.md](DESIGN.md) for the visual design system; this file does not repeat either.

## Hard Rules

1. **Repositories are the only files that touch Drizzle.** Services never import `drizzle-orm` or the
   DB client directly, and never reach into another module's repository. Cross-module access goes
   through the owning module's exported **service** (see `LabelsModule`'s `exports: [LabelsService]`
   for the pattern). A service that needs another module's data injects that module's service.
2. **CASL is the only authorization layer; nothing else backs it up.** Every route requires a session
   (global `AuthGuard`) unless decorated `@Public()`. Authorization is two layers, both required for
   anything with per-record rules: a controller-level `@CheckAbility(...)` / `AbilityGuard` gate, and
   inside the service a concrete-instance check (`ForbiddenError.from(ability).throwUnlessCan(...)`)
   for rules the controller gate can't express (ownership, org-scoping, status). Never skip the service
   layer check because the controller gate already ran — it can't see row data.
3. **New CASL rules are contributed, never hand-registered.** Add a subject's rules as an
   `@AbilityContributor() @Injectable()` class implementing `contributeTo()`, provided in its module.
   `AbilityFactory` discovers contributors via `DiscoveryService` at bootstrap; don't edit
   `ability.factory.ts` to wire a new one in. Contributor order must not matter: later rules may only
   **broaden** what earlier rules granted, never shadow or narrow them.
4. **`@repo/contracts` is the only place DTOs are defined.** Every HTTP body/query/param schema is a
   Zod schema there, decorated with `.meta({ id, description, example })`, wrapped with `nestjs-zod`'s
   `createZodDto` in the controller. Never hand-write a duplicate interface in `apps/backend` or
   `apps/frontend` for something a contract already defines.
5. **The OpenAPI artifact must never drift from the code.** After changing a contract schema:
   `pnpm --filter @repo/contracts build && pnpm --filter backend openapi:generate`, then commit the
   diff under `packages/contracts/openapi/`. CI's `openapi-sync` job fails the build otherwise — don't
   discover this after opening the PR.
6. **FSD import direction is one-way**: `app → pages → widgets → features → entities → shared`.
   Same-layer slices never import each other (compose one layer up instead). Every slice's public
   surface is its `index.ts`; import the slice, never its internals (`entities/label/lib/hooks.ts`
   directly, for example). `pnpm arch` (Steiger) enforces this in CI — treat a Steiger failure as a
   design smell to fix, not a rule to route around.
7. **Migrations run only through `db:migrate`, which uses `DIRECT_URL`.** `DATABASE_URL` is the
   runtime connection; keep the two separate even where they point at the same database, so a pooler
   can be added without touching the migration path. In staging and production, migrations run only
   from `deploy/hetzner/deploy.sh`, before the new app starts; never run them by hand against a
   deployed database. Never modify a migration file that has shipped — write a new one. Migration
   files come from `drizzle-kit generate` (`00NN_<generated-name>.sql`, e.g.
   `0032_unusual_the_twelve.sql`); don't hand-write, hand-number or reuse one.
8. **Every new user-facing string ships in all three locales.** `en.json`, `sv.json`, and `fi.json`
   under `apps/frontend/src/i18n/locales/` get the same keys in the same call. No hard-coded English in
   JSX; everything routes through `useTranslation()`.
9. **Never hand-edit `routeTree.gen.ts`.** It's regenerated by the TanStack Router Vite plugin from
   `app/router/routes/*.tsx`. Touch the route files; the generated tree follows.

General prohibitions:

- **No new dependency without asking first.** That includes a new `@better-auth/*` plugin, an MCP
  package or a NestJS add-on; propose it and wait.
- **Keep the diff to the request.** No drive-by refactors or renames of code the task didn't touch.

## When Uncertain

- **Stop and ask** rather than guess, especially for anything touching authorization rules, the
  requirement-resolution logic (rank → requirement set → org ancestry), or a migration against a
  shared database.
- **Domain questions load the `taido-domain` skill** (belt ranks, hokei groups, kobo classification,
  shogo titles, requirement sets, organisation ancestry) instead of being re-derived from the schema or
  from a pasted external spec. A wrong assumption here (e.g. treating `pattern.type` as a real column)
  has already cost rework once — see `docs/superpowers/plans/2026-06-30-grading-requirements.md`.
- **A new module or a new frontend slice starts from a skill**, not from scratch: `/add-module` for a
  backend module (schema → repository → service → controller → abilities → contract → tests),
  `/add-fsd-slice` for a frontend entity/feature/widget. Copying an existing module by hand tends to
  carry over stale imports or skip a required piece (a `.spec.ts`, an ability rule, an i18n key).
- **Adapting an external spec** (a design doc written against a different stack, or a plan template)
  goes through the `spec-to-plan` skill so the stack-specific gotchas get resolved once, explicitly,
  and recorded, instead of silently assumed.

## Definition of Done

A change is done when all of these hold:

1. `pnpm lint`, `pnpm typecheck`, and `pnpm arch` are clean.
2. `pnpm test` passes for every touched workspace; `pnpm test:e2e` passes if `apps/backend` changed.
3. New backend logic has a `.spec.ts` (service/repository unit tests, mocking the Drizzle client) and,
   for a new module, an `*.e2e.spec.ts` under `apps/backend/test/e2e/`.
4. New frontend logic with non-trivial conditional rendering has a `.test.tsx`; new API hooks have an
   `.api.test.ts`.
5. If a `@repo/contracts` schema changed: `pnpm --filter @repo/contracts build && pnpm --filter backend
   openapi:generate`, and the resulting diff under `packages/contracts/openapi/` is committed.
6. New UI strings exist in **all three** `apps/frontend/src/i18n/locales/*.json` files with matching
   keys.
7. If the change touched `apps/backend/drizzle/**`: the migration was generated with `db:generate`
   (never hand-written), and applied locally with `db:migrate` against `DIRECT_URL` before commit.
8. Run the `ci-verify` skill's checklist before opening the PR; it mirrors `.github/workflows/ci.yml`
   exactly, so a green local run means CI passes.
9. Commit messages and PR descriptions state what changed and why, matching the granularity of the
   `docs/superpowers/plans/*.md` this change was implementing, if one exists.

## Commands

```bash
pnpm dev                                 # frontend + backend + contracts watcher, concurrently
pnpm build                               # every workspace, respecting ^build deps
pnpm lint                                # ESLint, every workspace
pnpm typecheck                           # tsc --noEmit, every workspace
pnpm arch                                # Steiger FSD layer/import checks (frontend)
pnpm test                                # Vitest unit tests, all workspaces
pnpm test:e2e                            # Vitest e2e via supertest (backend)
pnpm --filter backend db:generate        # produce migration SQL from schema changes
pnpm --filter backend db:migrate         # apply migrations via DIRECT_URL
pnpm --filter backend openapi:generate   # regenerate packages/contracts/openapi/*
pnpm format                              # prettier --write
```

## Architecture

- **Backend module shape** (repeat this exactly; see the `add-module` skill): `schema/<n>.ts` (Drizzle
  tables) → `<n>.repository.ts` (only file touching Drizzle) → `<n>.service.ts` (business logic,
  cross-module calls via other services) → `<n>.controller.ts` (Zod DTO validation via `nestjs-zod`,
  `@CheckAbility` gates) → `<n>.abilities.ts` (`@AbilityContributor`) → `<n>.module.ts`.
- **Frontend slice shape** (FSD): `ui/` (components), `model/` (state, queries), `api/` (typed fetchers
  parsing responses through the matching `@repo/contracts` schema), `lib/` (pure helpers), all exposed
  through one `index.ts` per slice.
- **Auth**: better-auth mounted at `/api/auth/*` via `app.use(...)`, decorated `@Public()`. HTTP-only
  session cookie; the frontend has no Supabase client, anon key, or service key — the cookie is the
  only credential that reaches the browser.
- **Error envelope**: every error response is `{ error: { code, message, details? } }`, built by
  `AllExceptionsFilter`, shaped once as `ErrorEnvelopeDto` in `@repo/contracts/errors`.
- **Requirement resolution**: a student's applicable requirement set resolves down their
  organisation's ancestor chain (`OrganisationsRepository.getAncestorIds()`, a recursive CTE); `setId
  = null` means a global (federation-wide) row. See the `taido-domain` skill before touching this.

## Environments and Deployment

- **One origin per environment.** `https://taidohub.se` (production) and `https://staging.taidohub.se`
  (staging) each serve the SPA at `/`, the API under `/api` (better-auth at `/api/auth/*`) and the
  OAuth discovery documents at `/.well-known/oauth-*`, all through Caddy. Don't introduce a separate
  API domain or rely on cross-origin cookies.
- **Deploys go through GitHub Actions and `deploy/hetzner/` only.** Staging deploys after CI passes on
  `main`; production is a manual, reviewer-gated run of the same workflow. Never deploy, migrate or
  edit data on a server by hand outside the scripts in `deploy/hetzner/`.
- **Seed deployed environments only with `deploy/hetzner/seed.sh`.** It creates the sysadmin and the
  reference data. `SEED_CLUB_MEMBERS=true` is for local development only: the club roster holds real
  names and a shared password, and must never reach a server reachable from the internet.
- **Secrets live in `/opt/taidohub/.env` on each server**, never in the repo, a workflow file or a
  commit.

## Repository Map

- `apps/backend/src/modules/*`: one directory per domain module (organisations, users, memberships,
  belt-catalog, grading-requirements, rank-history, technique, pattern, labels, statistics, feedback,
  audit-log, feature-flags, user-impersonation, students, classification-category, profile, auth)
- `apps/backend/src/infrastructure/`: `ability/` (CASL factory + guard + decorators), `auth/`
  (better-auth wiring, session cache, current-user decorator), `database/` (Drizzle client, schema,
  seeds, migrate script), `email/`
- `apps/frontend/src/{entities,features,pages,widgets,shared,app}`: FSD layers, top to bottom
- `packages/contracts/src/*`: one file per domain area, Zod schemas + `.meta()` metadata
- `deploy/hetzner/`: Dockerfile, Compose, Caddy and the deploy, backup, restore and seed scripts
- `docs/superpowers/{plans,specs}/`: dated plan/spec pairs for shipped features — check before
  re-deriving a design decision that's already recorded there

## Testing

Vitest across all workspaces. Backend: unit specs mock the Drizzle client; `*.e2e.spec.ts` boots a real
Nest app against an ephemeral `postgres:16-alpine` container (see `.github/workflows/ci.yml`).
Postgres versions differ today (CI 16, local installs 17, Hetzner 18); the target is 18 everywhere.
Avoid features newer than Postgres 16 until CI is moved to 18. Frontend: component tests with
`@testing-library/react`, API hook tests against MSW handlers typed from `@repo/contracts`.
`pnpm --filter backend db:studio` opens a Drizzle DB explorer for local debugging.
